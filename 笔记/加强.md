# 基于 Agentic RAG 的知识库可信问答系统研究方案

## 一、项目定位判断  
- **定位合理性：** 采用“Agentic RAG 的知识库可信问答”这一方向符合当前大模型应用的发展趋势。相比于普通 RAG 问答系统，它融入了**Agent 规划和反馈**能力，能够自适应地进行多步检索、答案验证和引用证据【41†L49-L57】【43†L140-L149】。业内实践表明，Agentic RAG 能显著提升回答质量与可信度【55†L134-L142】【41†L69-L78】。  
- **提升点：** 相比传统单次检索-生成流程，Agentic RAG 的关键提升包括：多轮检索策略（可循环检索直到获取足够证据）、动态工具选择（如网络搜索、计算器等）、答案自检与纠错机制、以及证据引用闭环【41†L49-L57】【20†L143-L152】。它让系统更像一个智能问题求解者，而不仅是被动的信息检索器【2†L189-L196】【41†L69-L77】。  
- **适用岗位：** 此项目适合大模型应用研发岗位（如大模型应用算法工程师、RAG/Agent 工程师、NLP 算法工程师、AI 应用开发工程师等）。它既体现了应用工程能力（构建复杂系统）、又涉及检索算法和LLM agent设计，有算法和架构深度，有利展示技术功底。  
- **知识库场景：** 结合求职场景和技术背景，推荐使用**技术文档知识库**或**产品客服知识库**。技术文档（如开源框架或 API 文档）内容丰富、结构清晰，符合“技术面+工程实现”需求【48†L142-L150】【57†L94-L98】；产品客服文档则贴近实际应用。相对而言，个人知识库或企业内部闭源文档可用性较差；学术论文库适合科研岗但实现复杂；课程知识库偏教育领域。因此，技术文档或客服文档知识库最为合适。

## 二、为什么需要 Agentic RAG  
- **Naive RAG 的问题：** 传统单次检索-生成流程存在检索策略固定、多跳查询能力弱、易出现“凭空回答”（hallucination）、无法动态调用工具或自我纠错等缺陷【41†L49-L57】【52†L308-L316】。它对复合问题支持有限，回答有时会误用或缺少证据。  
- **Agentic RAG 的优势：** Agentic RAG 在每一步加入智能决策：它可**重写查询**、选择和组合多种检索工具（如向量库、BM25、网络搜索）【41†L69-L77】【43†L140-L149】；可**迭代检索**（多轮检索直到满意）；并在答案生成后加入**验证/批评步骤**检测内容一致性【20†L143-L152】【43†L147-L153】。这一模式使回答更准确可靠。  
- **需要 Agent 的模块：** 典型需要 Agent 处理的包括：**路由/规划(Router/Planner)**（根据问题类型选择检索方式或拆解问题）【43†L140-L149】；**答案生成(Answer)**（利用 LLM 综合证据）；**验证/批评(Verifier/Critic)**（检查答案与证据的一致性并判断是否需要二次检索）【20†L143-L152】【22†L288-L297】。  
- **无需 Agent 的模块：** 基础检索（向量索引、BM25 检索）、文档解析、缓存/数据库等可用传统算法和固定流程实现。例如向量搜索、倒排索引都是确定性的；答案拼接和页面显示等也可用常规代码。将不含主观决策的功能用非智能模块实现，可降低错误率和成本。  
- **是否需要多 Agent：** 如果知识库覆盖多个领域且需要领域特定检索策略，则可设计多智能体协作体系【55†L147-L156】。但对于单一领域知识库，可在一个流水线式 Agent 内完成任务即可，避免不必要的复杂度【55†L147-L156】。多 Agent 模式下，每个 Agent 可专注子任务（比如领域专家、工具调用者等），但会增加延迟和调试难度，应酌情采用。  
- **避免花瓶式设计：** 不应简单堆砌“Agent”名词，而要根据实际需求定义。每个 Agent 需有明确职责、输入/输出和触发条件。可合并过细的步骤以减少链路长度，避免过多冗余模型调用。要保证增加的智能体真正解决核心痛点，而非只为“高大上”而造。如查询规划、答案检验是核心场景，其它复杂工具可以按需增减。

## 三、系统架构设计

### 版本A（MVP，7–10天可完成）  
1. **功能范围：**  
   - 文档上传与解析（支持多格式文档导入）。  
   - 文档分段（固定长度或层次化切分）。  
   - 向量检索（基于 Sentence-BERT/BGE 等嵌入的相似度搜索）【48†L142-L150】。  
   - BM25/关键词检索（精准匹配补充）。  
   - 简单路由（如固定用向量或混合检索策略）。  
   - Prompt 拼接与答案生成（使用GPT类模型）。  
   - 证据引用（在答案中附上相关文档段落引用）。  
   - 简易答案校验（例如直接指令LLM若无足够信息则“抱歉我不知道”）。  
   - Web 可视化页面（使用 Streamlit/Gradio 实现交互式问答界面）。  
   - 基础评估（人工挑选若干问题验证功能）。  

2. **技术栈：** Python + LangChain（或LangGraph基础流程）+ HuggingFace/Sentence-Transformers + Chroma/FAISS + BM25库（如Rank-BM25或Elasticsearch）+ GPT-4/GPT-3.5 + Streamlit/Gradio + Docker。  

3. **模块结构：**  
   - `data/`: 文档存储与预处理。  
   - `retriever/`: 向量搜索和BM25检索实现。  
   - `generator/`: Prompt模板和LLM调用。  
   - `app/`: Web界面和用户交互。  
   - `utils/`: 辅助工具（分段、文本清洗）。  
   - `eval/`: 基础测试集和评价脚本。  

4. **实现难度：** **中等偏低**。主要任务是熟悉LangChain/RAG流程、构建检索和问答管道。可参考开源教程和样例（如Kubernetes 文档问答【48†L142-L150】），按步骤迭代开发。  

5. **简历价值：** 作为项目第一版，可证明基础检索增强问答能力。如：“实现**文档解析、向量检索、提示拼接**等完整RAG管道”并**对外界开放Web界面**展示问答结果。  

6. **面试可讲点：**  
   - RAG基本流程（文档分段、向量与BM25检索、LLM生成）【48†L142-L150】。  
   - 嵌入模型选择（如 Sentence-BERT）与向量库使用。  
   - 使用混合检索提升召回【52†L308-L316】。  
   - Prompt设计（让LLM引用证据），以及简单的答案拒绝策略【26†L479-L487】。  
   - 遇到的工程难点（大文档处理、参数调整等）。  

7. **不建议做的部分：**  
   - 避免立即引入复杂 Agents，如多角色协作或深度链式思考。  
   - 跳过过度优化（如复杂缓存、多级检索等）。  
   - 因时间紧张，不必马上做完善的评估系统或分布式部署。  

### 版本B（简历增强版）  
1. **功能范围：**  
   - 引入**Agentic 工作流**，使用 LangGraph 明确定义节点（Router Agent、Retriever、Answer Agent、Verifier 等）【26†L297-L305】【43†L140-L149】。  
   - **Hybrid 检索：** 同时使用向量和BM25（或HyDE技术【34†L74-L83】）进行查询，多策略检索以提高覆盖。  
   - **Reranker：** 使用交叉编码器对初步检索结果进行重新排序，提升上下文质量。  
   - **Evidence Extraction：** 从检索到的文档中抽取最相关段落或信息作为回答的证据。  
   - **Verifier/Critic：** 增加一个验证模块，对生成的答案进行事实一致性检测（使用LLM提示或嵌入对比）【20†L143-L152】【22†L288-L297】。  
   - **二次检索：** 如果验证失败，可触发**反思(Reflection) Agent**进行新的查询或补充检索。  
   - **拒答机制：** 设计阈值判断证据不足或答案不可靠时返回“无法回答”。  
   - **RAGAS 自动评估：** 集成 RAGAS 评估框架，使用其合成数据和指标（如 Context Recall/Precision、Faithfulness、Answer Relevancy）来自动评价系统【9†L36-L44】【13†L25-L32】。  
   - **日志追踪：** 使用 LangSmith 或日志系统记录每步操作和决策。  
   - **对比实验：** 对不同方案（基础RAG、混合检索、Agentic RAG 等）进行对比实验，量化提升效果。  

2. **技术栈：** Python + LangGraph（LangChain agents）+ LangSmith（监控）+ Chroma/FAISS + bge-m3/text2vec 等向量模型 + cross-encoder Reranker + RAGAS + FastAPI/Streamlit 前端 + SQLite/Postgres 存储。  

3. **模块结构：**  
   - `agents/`: 定义LangGraph节点，如 RouterAgent、RetrieverAgent、AnswerAgent、VerifierAgent 等，每个节点操作独立。  
   - `retrieval/`: Hybrid检索实现（组合向量与BM25）。  
   - `reranker/`: 交叉编码器或BGE Reranker模块。  
   - `verifier/`: 验证逻辑（调用LLM或模型评分）。  
   - `evaluation/`: RAGAS接入与脚本，比对实验。  
   - `ui/`: 更新前端，显示问答及证据链。  
   - `logging/`: 系统日志和LangSmith追踪。  

4. **实现难度：** **较高**。需要熟练掌握多 Agent 流程设计及调用，大量的模块开发和调试；同时处理评估流程、指标计算也具挑战。  

5. **简历价值：** 具备较高技术深度。可以写出“**基于LangGraph搭建多节点检索增强生成系统**，实现了动态路由、混合检索、交叉重排和答案验证，显著提升RAG问答的准确性与可信度”【52†L308-L316】【55†L134-L142】。并通过RAGAS评估量化了系统改进。  

6. **面试可讲点：**  
   - Agentic 工作流设计：角色划分、状态传递（MessagesState）【26†L327-L335】。  
   - 检索策略：混合向量+BM25以及 Parent-Child 分块【52†L308-L316】【57†L77-L85】。  
   - 答案验证：使用 LLM 判断回答与上下文一致性的具体实现【20†L143-L152】【22†L288-L297】。  
   - RAGAS 指标的意义与实验结果对比。  
   - 难点与优化：二次检索策略、收敛条件、缓存机制等。  

7. **不建议做的部分：**  
   - 避免过度依赖多 Agent 并发：若知识库单域，使用一个协调者模式即可。  
   - 图数据库（GraphRAG）可视为后续优化，不必强制引入（除非后续需求）。  
   - 人工参与（HITL）、权限管理等企业级功能，可根据需求酌情增加，但非必须。

## 四、Agent 角色设计  
**必要 Agent：**  
- **Router Agent（路由判断）：** 输入用户问题，判断问题类型并选择流程（使用向量检索、网络搜索或使用工具）【43†L140-L149】。  
- **Answer Agent（回答生成）：** 输入问题与检索到的证据，调用 LLM 生成最终答案文本。  
- **Verifier Agent（答案验证）：** 输入生成的答案和相关文档，判断答案是否被证据支持（如输出“可靠/不可靠”或检测幻觉语句）【20†L143-L152】【22†L288-L297】。  
- **Retriever Agent（检索器）：** 输入查询，负责执行向量和/或BM25检索，输出相关文档段落。  

**可选 Agent：**  
- **Planner Agent（问题拆解）：** 若涉及复杂多跳查询，可先将问题拆解成子问题；MVP 可合并在 Router 功能中。  
- **Evidence Agent：** 专门抽取关键句或摘要，但可由 Answer Agent内部实现。  
- **Reflection Agent（反思）：** 在验证失败时触发二次检索或重新提问，可由 Router 结合Verifier来协调实现，无需独立实体。  
- **Summarizer Agent：** 对多篇长文本进行摘要，提升多轮对话效率；若不强调对话连贯，可暂不用。  
- **Memory Agent：** 管理对话历史和长期记忆，用于多轮问答；单轮场景下可省略。

**输入/输出示例：**  
- *Router 输入：* 用户问题（字符串）；*输出：* 下一步行动（如`"use_vector_search"`或`"web_search"`）。  
- *Retriever 输入：* 问题文本；*输出：* 多个文档片段列表。  
- *Answer 输入：* 问题 + 文档片段列表；*输出：* 回答文本（含问题答案）。  
- *Verifier 输入：* 问题 + 回答 + 文档片段；*输出：* 是否可信（可为布尔或分数）。  
- （若有）*Summarizer 输入：* 相关文档；*输出：* 文档摘要。

**Agent 通信：** 利用 LangGraph 的状态传递机制（如 `MessagesState`），各节点顺序接收前一节点输出并更新状态【26†L327-L335】。节点间通过有向边连接，每个节点读取特定状态变量（如 `state["query"]`、`state["documents"]`、`state["answer"]` 等），完成任务后将结果写入状态传给下一节点。

**执行方式：** 一些步骤可**确定性实现**：如向量检索、BM25检索、文档分段等传统处理；而**LLM 参与**的步骤包括：Router 的高阶判断（可用简单规则或小模型判断）、问题重写、生成答案、验证答案真实性等【43†L140-L149】【26†L297-L305】。将确定性操作留给代码实现，以减少成本和错误，而由 LLM 负责需要自然语言理解的决策和生成任务。

**降低成本与延迟：** 控制 Agent 数量至最低：将简单判断集成到逻辑中，避免不必要的多轮 LLM 调用；对重复调用结果做缓存；在验证链中如果初次检索结果质量高，可跳过部分验证；尽量合并连贯的LLM操作（如在一次调用中完成多个判断）以减少接口开销。

## 五、检索系统设计  
- **向量检索：** 利用语义嵌入查找最相关文档片段。适用于理解复杂概念或词义的查询。MVP 必备方案【48†L142-L150】。缺点是对精确匹配(如代码片段、标识符)不敏感。  
- **BM25 关键词检索：** 用于查找包含关键词的文档，提供**精确命中**能力【52†L308-L316】。可捕捉纯粹字面问题（如函数名、产品编号）。在混合检索中作为“精准层”补充向量检索【52†L308-L316】。MVP可选用于提升召回，增强版建议使用。  
- **混合检索：** 同时运行向量和BM25搜索，整合结果以覆盖广泛信息。正如 Redis 博客所述，优秀的RAG系统通常同时使用两者【52†L308-L316】。适用于简历版及以上，可显著提高检索准确率。  
- **重排（Rerank）：** 对初步检索出的文档/片段集合使用交叉编码器或 Bi-encoder 重新排序，以提升最终输入到 LLM 的上下文质量。适合简历版，实现更精细的相关度排序；MVP 可通过简单阈值过滤代替。  
- **多查询检索：** 对多跳或复杂问题，将问题拆成若干子查询（可由 Planner Agent 生成），对每个子查询分别检索并聚合结果。适用于复杂推理场景，作为可选高级特性。  
- **查询改写（Query Rewrite）：** 使用 LLM 将用户提问转换为检索友好的形式（例如同义词扩展、澄清歧义）。可提高检索精度，对专业术语或长句特别有用。简历版可加入作为鲁棒性改进。  
- **Step-back Prompting：** 提前让模型“退一步”提炼查询的核心概念【30†L194-L203】。也可视作一种改写策略，帮助处理多维问题，适合复杂查询场景。注意不宜过度设计，视实现难度决定。  
- **HyDE（假设文档嵌入）：** 对于难以检索的查询，先让 LLM 生成一个假想的回答段落，再将其作为伪文档嵌入进行搜索【34†L74-L83】。可以提高难检索查询的召回率。在简历版或研究版中可尝试，MVP 可暂不使用。  
- **Parent-Child Chunking：** 将文档分为**大段（Parent）**和**小段（Child）**，先检索相关的Child，再返回对应Parent以保持上下文【57†L64-L72】【57†L79-L87】。解决长文档中上下文丢失问题，适用于具有清晰结构的知识库（如技术文档）【57†L94-L98】。在高级版本中可考虑加入。  
- **Graph RAG / Neo4j 检索：** 将知识库构建为知识图谱，用图查询回答多跳问题【36†L259-L268】【37†L246-L254】。图检索擅长发现隐含关系和多步推理路径。适合“域知识明确、关系丰富”的场景。作为进阶功能，如果使用此技术，需预先进行实体抽取和图谱构建。  

**各方法应用场景及实验设计：**  
- **MVP 适用：** 向量检索 + 简易 BM25/关键词检索，保证基本查询能力。  
- **简历增强：** 引入混合检索、交叉重排、查询改写等，以提升准确度。可针对每种方法做消融实验（如禁用 BM25、禁用重排后比较效果）。  
- **过度设计：** 像完全切换到 Graph RAG、复杂的异步多轮检索、HITL 等属于过度设计，仅在深入研究或特定需求下考虑。  
- **消融实验：** 可以搭建对比实验表：分别评估（a）单一向量检索，(b) 向量+BM25，(c) +Rerank，(d) +Agentic 逐步增强的场景，使用 RAGAS 指标比较检索召回率、答案正确率等【55†L134-L142】。

## 六、可信问答与答案校验  
1. **可信问答定义：** 答案必须严格基于知识库的检索结果，杜绝凭空生成信息。即回答中的每个陈述都有对应的文档证据支撑【36†L259-L268】【23†L71-L79】。系统输出应附带明确的来源引用，确保可验证性。  
2. **基于证据回答：** 在生成提示中要求 LLM “只能使用检索到的上下文回答问题”，并强制引用文档片段。例如提示模板可包括“请使用以下文档作为唯一信息来源”【26†L479-L487】。这样可约束模型依据给定证据作答。  
3. **来源引用：** 回答中尽量注明文档来源，形式可为嵌入引用标记或脚注（例如回答末尾列出文档 ID 和相关句段）。这让最终输出中的答案与资料库内容直接关联。面试官一眼能看到回答附带了具体证据出处。  
4. **幻觉检测：** 使用专门的 Verifier Agent。方法包括：  
   - *LLM 判别法*：向 LLM 提供回答和上下文，让其评分回答的“幻觉程度”（例如0–1分）【20†L143-L152】。  
   - *语义相似度*：计算回答与检索到的证据句向量相似度，若相似度过低则可能幻觉【22†L288-L297】。  
   - *采样一致性*：多次生成答案并用BERT等模型评估一致性，区别过度写实。  
   如果检测到高幻觉风险，触发重新检索或拒答。  
5. **证据不足处理：** 若检索上下文与问题关联度低（Context Recall/P@K指标很低），或Verifer判断无足够证据支持时，则返回“无法回答”或提示信息不足。这避免模型误答。系统设计拒答逻辑：例如如果多次检索都未发现相关内容，输出“对不起，知识库中没有足够信息回答此问题”。  
6. **冲突证据处理：** 若检索到多个文档相互矛盾，可设计两种策略：  
   - **保守拒答：** 如果无法统一事实源，就不直接给出肯定答案，告诉用户“所提供信息互相矛盾”。  
   - **并列呈现：** 在回答中同时列出冲突信息，并说明不同来源观点。这提高透明度，但需确保不引导错误结论。  
7. **Verifier 设计：** Verifier Agent 输入问题、回答与证据，输出回答是否可信。可以设计为两步：先抽取回答中的**每个声明**（claim），然后分别检查每条声明是否可从证据推导得出。**建议**将回答拆分成句子或关键陈述，逐条验证。最后如果所有关键陈述都被证据支持，则标记为“可靠”；否则触发拒答或二次检索【20†L143-L152】。  
8. **是否拆分成 Claim：** 拆分有助于细粒度验证，尤其答案包含多个事实判断时。不过也增加实现复杂度。视项目规模而定，高级版本可以采用逐条验证；MVP或B版可初步以整体答案一致性判别为主。  
9. **输出格式：** 设计明确的输出结构，以区分普通 RAG。比如：  
   ```
   Answer: "XXXXX."
   Sources: [文档ID-段落引用...]
   Confidence: Reliable/Uncertain
   ```  
   或 JSON 格式：`{ "answer": "...", "sources": [...], "status": "OK" }`。  
   强调证据引用和信心水平，使面试官一眼可见系统的“可信”特性，而不是只有一串文字输出。

## 七、评估方案  
1. **测试集构建：** 从所选知识库自动或手工生成测试问答对。可利用 RAGAS 合成工具自动从文档中生成多样问题【9†L36-L44】；同时人工编写典型问题，确保覆盖各类场景。  
2. **问题类型划分：** 测试集中需包括：事实型问题、总结型问题、多跳推理问题、对比问题、无答案问题（知识库外问答）、干扰信息问题（含多余噪声）等，以全面评估系统性能。  
3. **评价指标：**  
   - *Context Recall/Precision（上下文召回/精度）：* 评估检索出的文档片段中，有多少是正确关联到问题答案的。  
   - *Faithfulness（答对齐性）：* 答案内容与文档上下文的一致性，可使用 RAGAS 提供的无参考一致性评估【13†L25-L32】。  
   - *Answer Relevancy（答案相关度）：* 答案与问题的相关性，比如利用语义嵌入相似度。  
   - *Factual Correctness（事实正确率）：* 答案是否准确无误，可借助 RAGAS 的正确性指标或人工校验。  
   - *Refusal Accuracy（拒答准确度）：* 针对无答案问题，正确拒答的比率。  
   - *Latency & Cost：* 平均响应时间和调用成本（API调用次数/Token数）。  
4. **RAGAS 使用：** RAGAS 可用于无参考评估（嵌入相似度、LLM批评等）【9†L36-L44】【13†L25-L32】。我们可利用其集成的合成数据集和指标来自动评测，方便对比实验结果。  
5. **Agent 工具调用正确性：** 设计特定问题测试路由准确率，例如明确只需网络搜索或数学计算的问题，看系统是否正确触发相应工具。在日志中统计正确率。  
6. **对比实验：** 通过对照实验比较不同管道的效果：  
   - **Naive RAG**（向量检索 + 生成）  
   - **Hybrid RAG**（向量+BM25）  
   - **Hybrid RAG + Rerank**  
   - **Agentic RAG**（含动态路由+验证）  
   - **Multi-Agent RAG**（若适用）。  
   对比各方案在上述指标上的表现。如我们期望见到，与基线相比，Agentic RAG 在相关度和精确性指标上有明显提升【55†L134-L142】。  
7. **量化指标整理：** 将实验结果汇总为表格形式，明确展示精度、召回、正确率、拒答率、响应时间等数据。将性能提升用百分比或数值形式记录在简历描述中，如“回答准确率提升 X%，幻觉率降低 Y%”等。

## 八、工程实现方案  
1. **推荐技术栈：**  
   - **框架：** LangChain/LangGraph（多节点Agent编排）【55†L134-L142】。它为多Agent工作流提供清晰结构和监控支持（LangSmith）。  
   - **向量库：** Chroma 或 FAISS。Chroma 足够用于小项目，简单易用；也可升级至 Milvus/Qdrant。  
   - **检索：** BM25（使用 Elasticsearch 或 Rank-BM25 库）。  
   - **嵌入模型：** BGE-m3（适合多语言）或文本向量化（text2vec/RocketQA/Sentence-BERT）【48†L142-L150】【52†L308-L316】。  
   - **重排：** 双塔或交叉编码器 reranker（如sentence-transformers 中的 cross-encoder 模型）。  
   - **评估：** RAGAS（通过其 Python 库与LangChain/LlamaIndex集成）。  
   - **后端：** FastAPI 可提供HTTP接口，方便集成与扩展；前端则使用 Streamlit/Gradio 快速开发演示界面。  
   - **数据库/存储：** SQLite 或 PostgreSQL 存储对话历史和缓存；若用Neo4j，则部署图数据库。  
   - **其它：** Docker 化部署，方便移植；LangSmith 用于追踪调试。  

2. **LangGraph vs LangChain：** LangGraph 是 LangChain 的升级组件，更适合多Agent场景，具有显式的图结构编排和LangSmith集成【55†L134-L142】【28†L147-L155】。对需要复杂工作流的项目，LangGraph 提高可维护性。若只做简单RAG，也可以使用LangChain的SequentialChain，但项目重点是Agent，推荐用LangGraph。  

3. **是否需要 LlamaIndex：** LlamaIndex 提供便捷的知识库管理和查询接口，适合快速搭建。但由于本项目侧重Agent编排，可用LangChain/Retriever代替。LlamaIndex 的 RAGAS 集成是优点，可以引入其Evaluation功能，但不是必需。  

4. **向量库用 Chroma 是否足够：** 对于入门和中小规模项目，Chroma 性能足够，且易于部署。若数据量更大或需高并发，可考虑 Milvus 或 Pinecone。初步可从 Chroma 起步。  

5. **是否需要 Neo4j：** 只有当知识库适合知识图建模（如实体关系丰富）时才考虑。若主要文档文本检索，一般不需要。Neo4j 可为多跳复杂查询和上下文关联增益，但学习和构建成本较高，建议在高级版本或实际需求明确时再引入。  

6. **是否必须 Reranker：** 为简历演示提升效果，建议加入。Reranker 能显著提高检索结果的质量。但MVP非必需，重排序模型需要额外计算资源，可视项目重点决定。  

7. **前端 Streamlit 足够吗：** 对于Demo和简历项目，Streamlit 已足够实现对话式界面。它快速易用，能展示基本功能。若需要更复杂的UI或Web应用，可后续扩展。

4. **面试追问与回答：**  
   - **Q：Agentic RAG 和普通 RAG 有何区别？**  
     **A：** 普通 RAG 只是“一次检索一次生成”，无法动态调整。Agentic RAG 则在检索和回答阶段加入智能规划与验证步骤【41†L49-L57】【41†L69-L77】。它可重写查询、多轮检索、调用不同工具，并在生成答案后用 LLM 检查答案与证据是否一致【20†L143-L152】，因此回答更准确可靠。  
   - **Q：为什么要混合检索？**  
     **A：** 向量检索擅长捕捉语义相似度，但对精确术语（如产品ID、代码名）常常检索不到。BM25 等关键词检索作为**精准层**可以弥补这一弱点【52†L308-L316】。结合两者，可以提高检索的召回率和精确度。  
   - **Q：如何检测并处理幻觉？**  
     **A：** 我们设计了 Verifier Agent。它用提示让LLM判断回答是否被上下文支持【20†L143-L152】，或者比较回答与文档内容的语义相似度【22†L288-L297】。如果得分低，就认为存在幻觉，系统会拒答或尝试再次检索。  
   - **Q：RAGAS 是什么，如何使用？**  
     **A：** RAGAS 是一个评测 RAG 系统的工具。它能自动生成测试问题并给出多种指标（如答案与上下文的一致性、回答相关度等）【9†L36-L44】【13†L25-L32】。我们用它来自动化评估不同方案的效果，保证结果可量化。  
   - **Q：为何选择技术文档而非其他知识库？**  
     **A：** 技术文档内容丰富且结构化（如框架API手册），适合RAG场景，并且对求职岗位对口。在实际演示中，我们用开源项目文档作为知识库【48†L142-L150】，这样问题贴合开发者背景，面试官易理解项目价值。  
   - **Q：LangGraph 与 LangChain 有何不同？为什么选它？**  
     **A：** LangGraph 是 LangChain 的进阶组件，更适合复杂 Agent 工作流。它允许我们将任务分成多个节点，明确各 Agent 的输入输出【26†L297-L305】。我们选用 LangGraph 是为了实现可视化流程定义和监控，从而清晰展示多Agent协同逻辑。  
   - **Q：多Agent 系统是否必要？**  
     **A：** 多Agent（多专家系统）适用于多领域知识库【55†L147-L156】。如果只有单一领域，用一个Agent管道即可满足需求。我们的实验中，知识库为**单一领域技术文档**，因此采用了一个协同工作流（Router+Answer+Verifier等）而非多域Agent，以避免不必要的复杂度。

12. **高频追问与回答：**  
    - **Q：怎样确保答案一定是基于知识库？**  
      **A：** 我们在 Prompt 中严格要求 LLM “只能使用检索到的文档内容回答”，并在输出中附上具体引用【26†L479-L487】。同时，Verifier Agent 会额外检查答案与文档的一致性【20†L143-L152】，确保没有凭空回答。  
    - **Q：如何判断一个问题需要哪种检索工具？**  
      **A：** Router Agent 会分析问题关键词或语义。例如，如果问题包含专业术语或标识符，优先使用 BM25；否则使用向量检索。也可配置为 LLM 判别流程【43†L140-L149】。  
    - **Q：评估指标中“Context Recall/Precision”是什么意思？**  
      **A：** Context Recall 表示检索到的相关文档数量占所有相关文档的比例；Precision 表示检索结果中相关文档的比例。这反映检索质量。我们用这些指标配合 RAGAS 的 Answer 相关度和一致性指标评估整体性能。  
    - **Q：项目的难点是什么？**  
      **A：** 一个难点是平衡多轮检索成本与效果。我们设计了拒答阈值和校验机制，使系统在不确定时果断停止，避免无谓调用。另一个挑战是评估系统，需要设计实验确保对比方案公平，这里用了 RAGAS 进行自动化评测【9†L36-L44】。  
    - **Q：为什么不直接使用 LlamaIndex？**  
      **A：** LlamaIndex 对于单链式RAG流程非常方便，但本项目需要多Agent协同逻辑，LangGraph 在节点编排上更灵活清晰，因此优先选择了 LangGraph。
